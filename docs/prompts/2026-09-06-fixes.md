## 1. Page scrolls itself back up. FIXED, cause confirmed

**Cause.** `PipelineStepper` kept the active stage in view with
`element.scrollIntoView({ inline: 'center', block: 'nearest' })`.
`scrollIntoView` walks up to the nearest scrollable ancestor and, finding none
inside the strip, scrolls **the document**. The landing page runs a looping
teaser that advances a stage every couple of seconds, so the page was dragged
back to a fixed offset on every tick, and stayed there.

Measured in a real browser before the fix:

```
scrolled to 1400, then observed: 609, 609, 609, 609, 609, 609
FAIL page scrolled itself back
```

After:

```
scrolled to 1400, then observed: 1410, 1410, 1400, 1400, 1400, 1400
OK   page stayed put
```

**Fix.** Scroll the strip itself by computing the offset and setting
`container.scrollTo({ left })`. Never the document. `scrollTo` is guarded with
a `scrollLeft` fallback, because an exception thrown from that effect takes the
whole page down with it, and the stepper is decorative on the landing page.

That guard was not hypothetical: the first version of the fix crashed the
landing page in the test suite, because jsdom does not implement
`Element.scrollTo`.

## 2. Blank pages. NOT REPRODUCED

**This one is unresolved, and the cause is not established.**

Every route was checked in a real Chromium (Playwright), against both the dev
server and the production build, under four conditions: normal, `prefers-reduced-motion: reduce`,
400 ms of artificial latency on every module, and both together.

```
=== direct page loads ===
  OK   /                h1="Competitor analysis that shows its working"  chars=5190
  OK   /how-it-works    h1="The nine stages, end to end"                 chars=2181
  OK   /features        h1="Four agents, two gates, one document"        chars=4236
  OK   /about           h1="Built as a Final Year Project, designed as"  chars=2240
  OK   /pricing         h1="Placeholder pricing"                         chars=1759
  OK   /contact         h1="Get in touch"                                chars=998

=== click navigation from home ===
  OK   click How it works / Features / Pricing / About, all render

=== console / page errors ===
  none
```

Scroll position across navigation was also checked (scroll to 3200 on the
landing page, then click through to a shorter page): it resets to 0 every time,
so visitors do not land past the end of the new page.

### What was tried and ruled out

- **Lazy-route loading.** Rebuilt with route-level `React.lazy` in the previous
  session; suspected it first. Reverting the Suspense placement changed
  nothing: pages render either way, including with artificial latency.
- **Scroll position carrying across navigation.** Ruled out by measurement.
- **`prefers-reduced-motion`.** Ruled out.
- **A compile or transform error.** The dev server serves every page module at
  200 with no errors.

### One change kept anyway

`Suspense` was hoisted above `AnimatePresence` in both shells. This is *not*
established as the fix, the code comment says so explicitly, but it is the
ordering that stays correct as chunks get slower, so it is worth keeping.

### What is needed to close this out

One of:

- the browser console output when a page is blank, or
- whether it happens on `npm run dev` or on a built bundle, or
- which pages specifically, and whether by clicking or by typing the URL.

The most likely explanation given the evidence is a stale dev server or cached
bundle on the reporting machine: a hard reload, or restarting `npm run dev`,
would clear it. **That is a guess, not a diagnosis.**

## Test-harness gaps found and fixed

Both of these had been making the suite report success on things it was not
actually exercising.

| Gap | Effect | Fix |
|---|---|---|
| jsdom has no `IntersectionObserver` | Framer Motion's `whileInView` never fires, so every scroll-revealed section renders empty. Five route tests failed for a reason that had nothing to do with the routes | Stub in `src/test/setup.ts` that reports observed elements as intersecting |
| jsdom has no `Element.scrollTo` | The stepper's scroll fix threw and took down the landing page | Stub added, plus a runtime guard in the component |

| File | Covers |

disappearing entirely; they do not prove the animation/Suspense interaction is
correct. Only a browser check does that.
